# Distribution and signing: the sources behind ADR-0022

Each claim in [ADR-0022](../decisions/0022-distribution-and-signing.md), "What's true in
2026", with its source and what the source says, in our own words. Every source was
checked on **2026-10-25**. Where a claim no longer holds as written, the verdict says so,
and ADR-0022's amendment of the same date corrects it.

| # | Claim | Verdict | Source | What it says |
|---|---|---|---|---|
| W1 | An unsigned Windows installer shows "Windows protected your PC"; Smart App Control can block it outright. | Holds | [SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) (updated 2026-08-17); [Smart App Control FAQ](https://support.microsoft.com/en-us/windows/smart-app-control-frequently-asked-questions-285ea03d-fa88-4d56-882e-6698afdb7003) | An unsigned file shows the warning, and the user must choose "Run anyway". Smart App Control blocks unsigned files that its cloud service doesn't rate safe, and has no per-app override. |
| W2 | A newly signed installer is "unrecognized" until it builds reputation, which carries over to later versions with the same identity. | Holds, softened | SmartScreen reputation; [Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) (updated 2026-08-29) | Reputation has no published threshold: it can take weeks and many clean installs. Later files signed with the same publisher identity *can* avoid the warning; Microsoft doesn't promise it, and changing the certificate affects it. |
| W3 | EV certificates no longer skip the reputation wait; Microsoft removed that in 2024. | Holds | Code signing options; [Trusted Root Program requirements](https://learn.microsoft.com/en-us/security/trusted-root/program-requirements), §3.D.3 | EV once gave immediate reputation; Microsoft says that ended in 2024. The program stopped accepting EV code-signing certificates in February 2024 and removed their EV identifiers in August 2024. |
| W4 | Packages from the Microsoft Store are re-signed by Microsoft, so they show no warning. | Partly holds | [Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options); [SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) | Microsoft re-signs **MSIX** packages after certification. An **EXE or MSI** submitted to the Store isn't re-signed: the publisher must sign it with a certificate from a Trusted Root Program CA. Store installs show no SmartScreen prompt either way. |
| W5 | Since June 2023, signing keys must live in a hardware or cloud HSM, so no key file can sit in CI secrets. | Holds, clarified | [CA/Browser Forum code signing requirements](https://cabforum.org/working-groups/code-signing/requirements/) v3.11.0, §6.2.7.3 and §6.2.7.4 | Since 1 June 2023 a code-signing key must be made, kept, and used in a module certified to FIPS 140-2 Level 2 or Common Criteria EAL 4+. A cloud HSM or a signing service qualifies, so CI can call a signing service; it can't hold an exportable key file. |

## What wasn't verified

* SignPath's application form loads from a third-party script, so its fields weren't read.
* SignPath publishes no number for the "verifiable reputation" it asks of an executable.
* Microsoft's two pages disagree on which countries can validate an organization (the
  quickstart lists more than the code-signing options page). An individual is limited to
  the US and Canada on both.
